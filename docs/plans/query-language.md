# One query language for the Library search and blocking rules
Status: approved
Issue: diblaze/subwave#20
## Goal
A Library-tab search and a blocking rule are the same string in the same language (`live`, `title:/\b(live|remix)\b/`, `artist:="ABBA" OR tag:=christmas`, `genre:pop year:[2000 TO 2009]`, `-album:"greatest hits"`), parsed once by liqe, compiled to SQL for the Library tab and to a JS predicate for the pick path, so what the search box shows blocked is exactly what the rule blocks; every existing rule keeps its meaning without the operator touching it.

## Migration & rollback
- Mapping (`legacyRuleQuery`, E5 semantics preserved line for line): `genre [A,B]` → `genre:"A" OR genre:"B"` (refine); `tag/mood/album/title [A]` → `field:="A"` (nameKey-exact); `artist [A]` → `artist:="A"` (whole credit or any credited act); any `/re/` value → `field:/re/` (unescaped `/` in the body escaped); `playlist [id]` → `playlist:"id"`; values quoted with `JSON.stringify` (E3). Season and show scope are untouched.
- Load: `coerceStoredRule` derives `query` in memory for a `field`+`values` record and keeps both keys; `blocklist.json` is not rewritten until the next mutation (E7 :193), and a rewritten file still carries `field`/`values` for every rule the operator has not edited.
- Rollback to a pre-S2 build: legacy-origin rules load unchanged (`z.object` strips `query`, E6); rules created or edited in the new editor have no `field`/`values` → the old `coerceStoredRule` drops them loudly at boot (E7 :173-175, "dropped N unparseable rule(s)") and they stay inert, not wrong; rolling forward restores them unless the old build persisted a mutation in between. Before a rollback: `cp state/blocklist.json state/blocklist.json.bak`.
- Library search: `/re/` typed into the box keeps working (bare regex = implicit field, E2); `%`/`_` in plain text stop being LIKE wildcards (now escaped), and `*`/`?` become wildcards — the one visible behaviour change, named in the S1 PR body.
## Deferred (YAGNI)
- Stored folded columns (`title_fold` …) + indexes instead of `fold()`/`name_key()` per row — E25 puts LIKE at 1.8 ms/7k; a leading-`%` LIKE cannot use a B-tree anyway. Reopen when a keystroke search exceeds ~200 ms (≈50k+ tracks); then a migration writing the folded text from `upsertTrackMeta` (not a generated column — a JS UDF inside a generated column makes the file unopenable by any client without it) plus FTS5 trigram for substring.
- liqe in the web bundle (client-side parse, highlighting from `location`) — reopen when the operator asks for syntax colouring; S3's server preview already gives inline errors with an offset.
- Field-scoped grouping `title:(live OR remix)` — open a liqe issue/PR (nearley grammar) rather than a pre-parse rewrite; reopen when upstream lands it. Until then the UI hint and `search-query.ts` header name the workaround (E1).
- Show filters / smart playlists on the same query (operator step 5) — reopen when a show needs more than `genres`/`moods`; `compileSql` + `compileJs` are the entry points, the show-filter JS/SQL pair (E20) is the pattern.
- SQL-backed `matchCount`/preview (`filter({ query, includeUntagged: true })`) — reopen when the `ruleMatchRows` walk is measurably slow on the Blocked tab (~50k+ tracks); the SQL twin is already there.
- Friendlier playlist tokens (name instead of id in the row line) — reopen if an operator reports the id as unreadable; ids are what `remapIds` can rewrite.
- `GET /library/liked` `q` through the query language — reopen when a Liked search box lands (no UI sends it today, E13).
